# 作业锁竞争与退出占用验证

日期：2026-11-12（America/Los_Angeles）。基线 `40ee7ab`；Windows x64，开发 Node 26.13.0、便携 Node 24.19.0。仅使用生成素材和隔离副本；原始日志位于忽略目录 `.local/maintenance/race-*.log`。

## 根因与修复证据

### 登记锁释放与读取交错

`acquireGate` 用排他创建读取持有者身份，但 EEXIST 之后、readFileSync 之前，原持有者可正常释放 owner.json。旧实现把此时 ENOENT 直接抛给 worker；`acquireShared` 只重试 BUSY，导致尚未处理素材就发布 exitCode=1，且没有 summary。这解释了处理失败和重试后读取 summary 异常的同类症状。

新增回归在真实处理与 retry worker 中，暂停 EEXIST 后的读取，等父进程释放锁再继续。修复前两条作业均稳定产生 ENOENT/exitCode=1/无 summary；锁单测同样失败。修复只把这个窗口的 ENOENT 转为带 lockName 的 BUSY，复用原有最多 5 秒等待；不重交作业、不换幂等键、不跳过锁。坏 JSON、无效 PID、权限错误、活持有者与过期身份回收另有安全断言。

### 孤儿 worker 在进程退出前释放占用

复现全量时另发现既有 parallel 用例在后续作业结束时，原 worker 仍存活。worker 原本在 runJob finally 删除独立占用；父进程已死且 worker.json 未发布时，这会丢失最后的活进程证据。

新增测试把 worker 固定停在 beforeExit，模拟缺失 worker 身份及死亡父进程。修复前观察者错误返回 done=true；修复后占用保留到 PID 确认退出，后续冲突项保持 queued、没有 dispatch，独占维护仍拒绝。放行退出后原作业及等待作业均成功，占用可回收。原有 parallel 的退出断言未删除或放宽。

两项修复共用核心，无新增公共能力或格式变更；桌面、CLI、MCP stdio/HTTP 与 HTTP API 自动复用，应用 /7、job /5、execution /2 保持不变。

## 历史证据边界

[上一轮两次失败](2026-11-12-service-management.md)没有保存完整 worker 错误，不能逐次追溯证明其唯一根因。本轮已确定并修复能稳定产生相同症状的登记锁竞争，同时修复新发现的孤儿退出窗口；不把反复通过本身作为根因证明。

修复前桌面/services 定向连续 20 轮通过，说明自然复现不稳定；全量初轮触发 parallel 退出断言，随后六轮全量中一轮出现 application 恢复摘要缺失。新增门闩回归提供确定性失败证据。沙箱曾阻止回环连接，放行测试权限后继续；编辑期间两轮因新测试尚未登记而被分层检查阻止，不算完成验收。新孤儿测试首次修复后因夹具重复写同一输出而失败，改为冲突预览等待项后通过，未改变输出保护规则。
