# 持久串行队列

状态：已实现单安装 FIFO、执行并发度 1。应用/响应 `/4`，HTTP `/api/v4`，持久 job `/3`，启动声明 dispatch `/1`。源码：`application/{service,queue,job-session,lock}.js`。决策见 [ADR 0013](../decisions/0013-persistent-fifo.md)。

## 提交与调度

所有入口仍调用 submit/status/cancel 等同一套公共动作。提交锁内校验幂等身份、依赖与请求，分配递增 sequence，排他写入并 fsync `data/jobs/v3/<jobId>/job.json`；其中保存规范化请求、原公共请求、持有会话 UUID 和 PID。全部未结束作业最多 100 个，超限以 BUSY 拒绝且不占幂等键。相同键/请求仍重放原 ID；已结束及清理后的身份保留，序号不会被应用回收。

公共响应层对 submit/cancel 的短暂提交锁竞争最多等待 5 秒，使用同一幂等输入重试；容量满、会话关闭、权限和其他错误不自动重试。低层同步 dispatch 仍可返回 BUSY。等待超过上限也返回 BUSY，调用方可稍后用原键确认登记结果。

每个有自己作业的应用服务每 100ms 尝试一次调度。**提交锁是唯一调度选主边界**：在锁内读取整个队列，按序号确认队首及所有运行记录；只有队首的原持有会话能启动它。无需常驻后台进程或每个等待项一个进程，也不会把启动权限转交其他会话。扫描、分析、处理、恢复和依赖安装共用同一队列。

启动前重新规范化公共请求、核验启动上下文权限及路径，规范化结果必须与入队快照一致；独立 worker 再按步骤版本及任务/恢复哈希验证。排队时配置或工具被修改不代表允许换版本执行。启动前先持久写入 dispatch/1，之后创建 request 和 worker；进程记录、状态及 exit 沿用已有机制。只有退出已确认才公布最终状态并派发下一项，执行锁、任务锁和文件提交保护继续保留。

外部维护暂时持有执行锁时队首继续等待。存储清理取得提交/执行锁后还检查等待和运行项，存在未结束作业就返回 BUSY；队列元数据和 dispatch 不在可删明细中。

## 状态、取消与退出

| 情况 | 行为 |
| --- | --- |
| 已登记、尚无启动声明 | `phase:queued, done:false, sequence, queuePosition`；位置从 1 开始，包含执行中作业，不是预计时间 |
| 取得启动权 | 写 dispatch 后由 worker 发布 starting/scanning/processing 等原阶段 |
| 排队取消 | 同提交锁内写最终 cancelled/exitCode 2 状态，不启动 worker、不创建素材任务或报告 |
| 运行取消 | 写取消标记，在文件边界结束；done 仍等待进程退出 |
| 桌面、CLI、stdio 正常退出 | 取消自己所有等待项，对自己的运行项协作取消并等待退出 |
| HTTP 客户端断开 | 服务继续持有作业；HTTP 服务正常退出才取消自己所有作业 |
| 纯观察者关闭 | 不影响其他入口作业；显式 cancel 仍可在当前权限内跨入口执行 |

CLI submit 继续等待最终结果，默认不自动超时；Ctrl+C/SIGTERM 请求取消。桌面当前仍一次配置/提交一个本会话作业，但遇到其他入口占用会排队；HTTP/MCP 应用服务可以持有多个等待项。作业中心增加排队筛选、位置和取消入口。

## 崩溃与保守恢复

等待项持有进程死亡后返回 INTERRUPTED，后续存活持有者的队首可以继续；不会在新上下文自动接管旧权限并执行。启动声明落盘后，即使 worker 记录缺失也不会再次启动该 ID。若 worker 仍活着，后续项等待；worker 使用父进程存活检查及文件边界取消。已有素材任务继续通过显式 resume/retry 恢复；同幂等键只返回旧作业。

进程锁以 PID/token 判活，不采用超时强抢或心跳超时杀进程；PID 重用、坏元数据、丢失退出记录可能保守阻塞，需要人工核对，不能自动认定可重跑。未确认退出的进程不能被新调度者替换。此实现是会话共同参与的持久队列，并非退出所有应用后仍自动运行的后台服务。

## 版本与性能边界

旧 `/api/v1`、`/api/v2`、`/api/v3` 返回 410。旧 job/1、job/2 不读取或迁移，新根出现旧 schema 明确拒绝；未知 dispatch 版本拒绝。task/report/settings 及扩展契约不变。升级时关闭旧入口并更新 EXE/核心/MCP；不能自动把旧作业请求或幂等键重新提交给新版本。

队列扫描当前是同步全目录读取，作业列表和位置查询也未建立索引；历史量大时需进一步优化，100 项上限限制等待容量而不是历史记录数量。不同安装的锁独立，不解决跨安装共享目录冲突；无优先级、重排、等待超时、全局目录读写锁或有限并行。下一阶段若需要持续后台执行，先设计明确的服务所有权和租约，再考虑不相交资源的有限并行。

验证包括 queue.test.js 的跨会话 FIFO、多项提交、取消、退出、死队首、未确认启动、版本变化及容量；application/unified/http、MCP 双传输、存储安全和原生排队 E2E。实际结果见[项目状态](../project-status.md)。
