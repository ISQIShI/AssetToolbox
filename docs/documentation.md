# 文档管理规范

状态：已采用。适用范围：本仓库的贡献者与 AI 开发会话。

文档与代码共同版本管理，描述可验证的当前行为，并保存影响后续开发的重要决策。中文是主要语言；路径、代码标识符、协议字段和命令保持原样。

## 分层与唯一维护位置

| 位置 | 维护内容 | 不应放入的内容 |
| --- | --- | --- |
| `AGENTS.md` | AI 阅读顺序、不可破坏的约束、开发与提交规则 | 全量接口字段、长篇设计推导 |
| 根 `README.md` | 项目介绍、发行范围、用户指南入口 | 冗长教程、内部调度实现细节 |
| `guides/` | 对外使用、依赖安装、MCP/CLI/HTTP 接入、从源码开发部署与排错 | 内部架构推导、逐轮验收日志、真实凭据 |
| `docs/README.md` | 全部开发文档的导航和任务阅读路径 | 重复的架构正文 |
| `docs/architecture/` | 当前结构、状态流转、协议与数据契约 | 尚未实现的功能承诺 |
| `docs/design/` | 界面视觉主张、设计令牌、组件与文案规范 | 组件实现细节、协议字段 |
| `docs/development.md` | 开发命令、验证范围、提交规范 | 每次运行的完整日志 |
| `docs/project-status.md` | 当前基线、最近验证摘要、限制及下一步，目标不超过 100 行 | 逐轮历史、完整日志、重复架构说明 |
| `docs/verification/` | 按日期和主题保存环境、代码基线、命令、结果、EXE 摘要与未覆盖范围 | 尚未运行的成功声明、真实素材与秘密 |
| `docs/archive/` | 历史快照和失效方案，注明替代文档 | 当前规则或未标注的有效待办 |
| `docs/decisions/` | 对兼容性、边界或长期维护有影响的设计决策 | 小型文案调整记录 |
| 就近 `README.md` | 模块扩展、桌面构建等专题操作细节 | 与上级文档重复维护的完整规范 |

每项规则只在一个位置完整定义，其他文档通过相对链接引用。用户教程写在 guides 并从其 README 与根 README 导航；docs 中开发指南维护贡献/验收规则，架构专题维护协议事实，用户指南只摘取完成任务所需步骤并链接深入内容。版本号、工具要求优先引用锁定文件和提供方记录，避免多个手工清单漂移。文档随版本标签固定，已发布说明不回写。架构文档解释模块契约与调用关系；具体数值、字段校验和执行逻辑仍以列出的源码为准。文档中的“计划”必须明确标注，不得混写为当前能力。

## 命名与结构

文件使用小写英文和连字符，如 `frontend.md`；正文标题使用中文。普通专题包含范围、源码入口、主要流程、边界条件和验证入口。协议及数据格式优先使用表格与最小示例；跨进程流程使用 Mermaid，并同时保留文字解释。

重大架构决策使用连续编号 `NNNN-简短英文主题.md`，结构见[决策模板](decisions/template.md)。状态为“提议”“已采用”“已取代”或“否决”。已采用记录保留历史背景；新决策以新文件取代旧记录，双方互相链接。记录既有实现时标明“现状补录”，不要虚构历史讨论。

## 更新责任与触发条件

实施变更的人或 AI 同时维护相关文档，在同一提交或同一个 PR 中交付：

- 界面流程改变：更新前端架构及面向用户的说明。
- 视觉、令牌、组件样式或界面文字改变：更新前端设计规范；令牌表与 `desktop/src/styles/tokens.css` 保持一致。
- action、payload、状态或错误改变：更新通信协议、TypeScript 类型和桥接测试。
- 统一应用能力改变：同时核对桌面操作路径、CLI 命令/帮助、MCP 两种传输、HTTP 路由、schema、授权拒绝及跨入口行为验收；仅入口特有能力可只更新对应入口。不能只更新核心后宣称功能完成，见[入口覆盖](architecture/service-management.md#后续公共能力的交付要求)。
- 配置、任务事件或报告改变：更新持久化专题，说明版本与读取/拒绝策略，补对应契约测试。
- 类型、操作、提供方 schema 或接口改变：更新扩展契约、后端专题与契约测试。
- 构建、依赖、目录或验证命令改变：更新开发指南及桌面 README。
- 新增或移动文档：同步索引和所有入站链接。
- 跨会话开发结束：更新项目状态中的完成项、验证结果、剩余问题及下一步；已解决条目删除或改为已解决，避免积累失效待办。

改动不涉及文档描述的行为时，无需机械更新每篇文档的日期。纯文档修订也无需新建决策记录。

## AI 开发与交接流程

1. 阅读根指南、文档索引、项目状态和对应架构专题，检查 `git status` 与最近提交。
2. 跟踪入口、调用方、实现和相关测试，明确用户授权范围及兼容性约束。
3. 先实施和验证当前需求，再将最终行为同步到文档；不要将未执行的测试写为通过。
4. 更新项目状态的当前概况和最近验收表；详细证据写入 `docs/verification/YYYY-MM-DD-topic.md` 并登记索引，原始日志留在忽略目录 `.local/`。本轮复测更新同一记录；后续变更另建记录，不改写旧验证事实。
5. 检查 Markdown 链接、命令工作目录、字段名及暂存差异，使用 Conventional Commits 提交。

任务较大时可在 `docs/plans/` 新建方案，标注状态、目标、边界、步骤、验收与关联决策。完成后把有效结论写回长期文档，再按需要移到 `docs/archive/`，标明失效原因及替代文档；归档内容不参与当前开发规则。目录按需创建。

## 项目状态的滚动维护

固定顺序为“当前基线 → 最近验收 → 已知限制 → 下一步”。每次替换对应事实，不追加日期章节；已完成待办移出，具体行为只链接架构专题。仅保留最近一轮验收摘要，历史通过[验证索引](verification/README.md)追溯。大规模整理前归档原文并修复相对链接，历史标题必须注明非当前规范，避免 AI 把旧版本或已完成工作当成待办。

## 文档验收

- 所有新增文档均可从索引到达，相对链接对应真实文件。
- 示例不包含真实用户绝对路径、配置、任务记录或秘密。
- 命令注明运行目录和前提；测试通过、跳过、失败、未执行分开说明。
- 新旧行为、现有能力和后续建议能明确区分。
- PR 说明列出更新的文档或说明无需更新的原因。
