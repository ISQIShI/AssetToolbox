# 任务体积统计与打开文件夹验收

日期：2026-11-16。基线 `53ea408`；代码在 `445bc28`，本记录与文档同步在其后一次提交。用户要求在任务详情里加体积统计和“打开文件夹”。

## 变更与边界

- **核心**：`tasks.js` 的任务摘要 `info()` 新增四个只读字段——`totalBytes`（固定清单在扫描时的总大小）、`originalBytes`、`outputBytes`、`savedBytes`（只累计已完成文件的结果记录）。它们由既有的清单快照和结果记录推导，**不改变任务文件格式（task/2）、请求 schema 与任何版本号**。`tasks` 动作与作业状态里的 `task` 原样透传摘要，因此桌面、CLI、MCP stdio/HTTP 和 HTTP API 同时得到这些字段，没有新增入口专用逻辑。
- **桌面**：任务详情新增“体积”分组（处理前、处理后、体积变化及百分比）；核心没有给出体积字段时整组不显示。详情里的来源、写入、备份各带一个“在资源管理器中打开”的按钮。
- **原生命令** `open_folder`：只接受绝对路径且必须是现有文件夹，否则返回错误并由界面显示。属于桌面专属功能（打开系统窗口），不经过核心，其他入口没有对应能力。
- 没有改动：任务的续跑、重试、恢复语义与权限；恢复不回退体积数字；失败与待处理文件不计入体积。

## 未执行与限制

- `open_folder` 的成功路径（真的弹出资源管理器窗口）没有自动化用例，也没有在本机实际点开过；只验证了三种拒绝情况和界面传入的路径。
- 原生 E2E 没有新增针对体积分组的断言，体积数值由核心测试和组件测试分别覆盖。
- 没有为 CLI、MCP、HTTP 单独新增体积字段的断言：三者透传同一个摘要对象，既有跨入口测试全部通过。
- 联网 E2E 未运行：没有修改对应代码。
- 体积只统计已完成的文件，恢复原文件后数字不回退；对结果记录里没有体积的旧记录按 0 计。
- 备份文件夹被移动或删除后，按钮仍然显示，点击时才提示不存在。
